# Lesson 11 — EC2 (Compute)

## 1) What it is

**EC2 (Elastic Compute Cloud)** is a virtual server in AWS.

You choose:

- CPU/memory size (instance type)
- OS image (AMI)
- network placement (subnet + security group)
- disk (EBS)

## 2) Why it’s needed

Your application code needs somewhere to run.

EC2 is the simplest “server” building block:

- you can run a web app
- you can run background jobs
- you can install packages and configure the OS

## 3) Where it fits in our architecture

In AcmeShop:

- EC2 instances run the application
- EC2 instances live in **private app subnets**
- ALB sends traffic to EC2
- EC2 connects to RDS

## 4) How it works (basic internal flow)

When you launch an EC2 instance:

1) AWS provisions compute capacity
2) Your chosen AMI boots
3) The instance gets a network interface in your subnet (VPC)
4) Your security groups determine allowed traffic
5) Your app starts (manually or via user data/systemd)

## 5) How it connects with other AWS services

- VPC/Subnets: where EC2 runs
- Security Groups: firewall rules
- EBS: disks attached to EC2
- ALB: routes HTTP/HTTPS traffic to EC2
- IAM Role: gives EC2 permission to access S3/CloudWatch
- CloudWatch: metrics/logs

## 6) Real-world example

AcmeShop app tier:

- 2+ EC2 instances (across 2 AZs)
- Each instance runs `acmeshop-api` on port 8080
- ALB forwards requests to port 8080

## 7) Common mistakes beginners make

- Putting EC2 in a public subnet “so I can SSH” (use a safer approach later)
- Opening SSH (22) to the world (`0.0.0.0/0`)
- Forgetting to use an IAM role and then adding access keys to the server

## 8) Interview explanation

"EC2 provides virtual servers. I run the application tier on EC2 instances in private subnets behind an ALB, attach least-privilege IAM roles for AWS API access, and use Auto Scaling across multiple AZs for availability and scaling."

## Summary

- EC2 = virtual servers for running application code
- Place app EC2 in private subnets behind a load balancer
